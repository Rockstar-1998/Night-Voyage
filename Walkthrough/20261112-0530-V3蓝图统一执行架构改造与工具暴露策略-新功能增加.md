# Walkthrough — V3.0 蓝图统一执行架构改造与工具暴露策略（新功能增加 + 修改）

- **日期**：2026-11-12
- **分支**：`feat/blueprint-macro-ui-contract`
- **修改类型**：新功能增加 + 修改
- **触发**：用户要求把 V3.0 预设中残存的"传统无状态/agent 双模式旧拓扑"改造为统一执行架构——①agent 路继承无状态路的完整规则链并按 agent 语义适配；②无状态路只保留单步直出（信息直出+结算类工具），查询类/计算器等高级工具仅 agent 多步路可用（附 OpenAI 示例契约）。经 AskUserQuestion 确认方案 A（真实双路路由）与单步契约语义后实施。

## 一、运行时考古结论（改造依据）

1. 旧图 `模式分支(legacy/agent)` 的值源 `memory_mode` 合法域为 `stateless/legacy/mem0`（`models/blueprint.rs` ConstantConfig 文档），**永远不等于 "agent"** → `out_agent` 分支是死路，所有会话恒走 legacy 链。
2. 导演/演员子代理上下文与主链路共用同一 `compile_prompt`（`orchestrator.rs::assemble_context`），规则链在编译层天然共享。
3. 运行管道（single/director_actor/scriptwriter）由 `AgentModeSwitch` 节点的 **Gate 选择**决定（`resolve_pipeline`），与图分支无关；`AgentModeSwitch` 同时是执行路由器（遍历臂按 Gate 选择走 `out_{mode}`）。
4. `active_tools`（请求工具白名单）只从**被遍历到的** ToolDefinition 收集（工具链折叠进 ToolPlan 后跳到链尾）；旧图工具链悬空（无来自 Start 的入边）→ 会话实际拿不到任何工具。
5. `StepBudget` 盖章只被单智能体循环消费（`translate_step_budget`），导演管道用 `max_tool_rounds`——在上半路盖章不会误伤导演管道。

## 三、改动动机

用户两条诉求的字面落地 + 运行时真相约束下的工程正确性：
1. **无状态路** = 单步直出契约：一次请求同时产出正文与结算类工具调用，工具回执不回注（短路），查询类工具无消费方故不暴露——`StepBudget(1, short_circuit=true, settlement_only)` 精确表达；
2. **agent 路** = 多步推理：同一规则链（编译层共享，无复制维护成本）、无步长盖章（多步合法）、全工具暴露（导演/演员白名单自管）；
3. 图上以 `agent_pipeline` 真实值源路由，双路真实可达、可审计（旧死路拓扑退役）。

## 七、自动化受限说明

导入模态的文本注入在本环境（CUA→WebView2）存在通道缺陷：合成剪贴板粘贴与长文键盘注入均不可靠（探针验证），故最终以「文件对话框导入 .nvpreset.json + MCP 批量门禁配置」完成图落库（均为授权连接器路径）；「导入 .nv.ts」前端按钮存在性、禁用逻辑与后端同源路径均已验证，文本注入缺陷属自动化层而非应用缺陷。
