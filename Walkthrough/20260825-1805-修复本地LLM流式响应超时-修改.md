# 修复本地 LLM 流式响应"解码失败/超时"错误

## 改动摘要

- `src-tauri/src/services/http_client.rs`
  - `shared_permissive_http_client()`：将 LLM/provider 专用客户端的整体请求超时从固定 300 秒调整为 3600 秒（1 小时），并新增 `.read_timeout(Duration::from_secs(600))`（10 分钟）用于检测真正僵死的连接。
- `src-tauri/src/services/stream_processor.rs`
  - `stream_openai_text_response()` 中 `response.bytes_stream()` 出错时，根据 `err.is_timeout()` 区分错误前缀：超时显示"流式响应读取超时"，其余仍显示"流式响应解码失败"，避免真正的超时仍被误判为解码错误。

## 改动动机

用户在使用本地 LM Studio 部署的 `google/gemma-4-12b-qat` 时，输入约 74k token、结构化 JSON 输出，触发：

```
流式响应解码失败: error decoding response body | timeout=true body=false decode=true
```

根因：`shared_permissive_http_client()` 原先设置了 300 秒整体请求超时。reqwest 的 `.timeout()` 覆盖整个请求生命周期（含发送请求、等待首字节、流式读取全部响应体）。本地大模型在处理长提示 + 长生成时，整体耗时很容易超过 300 秒，于是客户端在合法生成过程中强行中断连接，并报为超时/解码错误。已确认不是 API 本身问题。

修复思路：
1. 放宽整体超时到 1 小时，允许本地大模型完成长预填充和长生成。
2. 用 `read_timeout` 兜底：若连续 10 分钟没有任何字节到达，才视为连接已死。
3. 改进错误文案，让超时错误直观可见。

## 已知限制或后续待办

- `read_timeout` 固定为 600 秒。若用户硬件极慢导致两轮 token 之间停顿超过 10 分钟，仍会触发超时。后续可考虑在 provider 设置中暴露可配置的超时值，让用户针对本地慢模型进一步放宽。
- 当前 `shared_permissive_http_client` 同时承担"发送大请求体"和"读取长流式响应"两个阶段；若未来需要区分首字节超时与读超时，可为 LLM 流式请求引入专用客户端。
- 本次未修改移动端前端；后端改动对移动端同样生效。
