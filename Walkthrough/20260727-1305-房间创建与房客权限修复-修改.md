# 房间创建与房客权限修复

修改类型：修改

## 1. 改动摘要

### 问题背景
用户报告「创建联机房间时有错误」，最初截图显示 `(code: 787) FOREIGN KEY constraint failed`。
经诊断日志（`[room-create][DIAG] conversation_id=25 exists=Some(true)`）确认：创建房间时
会话 25 真实存在，原 787 错误未在当前版本复现。但复现过程中暴露了三个真实缺陷：

| # | 问题 | 根因 | 修复位置 |
|---|------|------|---------|
| 1 | 房客加入房间时 `build_context_snapshot` 失败：`(code: 1) no such column: wb.name` | `world_books` 表只有 `title` 列（无 `name` 列），但代码引用 `wb.name` | `src-tauri/src/services/chat_service.rs:2019`、`src-tauri/src/network/mod.rs:1312` |
| 2 | 房客的会话详情也显示「关闭房间」按钮，房客可触发关闭房主房间 | `SessionSidebar` 仅按 `roomStatus === 'open'` 判断，未区分房主/房客 | `src/components/SessionSidebar.tsx`、`src/App.tsx`、`DesktopViewProps` |
| 3 | 创建房间时若 `conversation_id` 为孤儿 id（会话已删），会静默触发 DB 的 787 FK 错误 | `room_create` 未做前置存在性校验，DB 抛晦涩 FK 错误 | `src-tauri/src/commands/rooms.rs:97` |

### 具体改动

1. **chat_service.rs / network/mod.rs**：将 `SELECT wb.name` 改为 `SELECT wb.title`
   （两处构建 host world book 名称的逻辑）。

2. **rooms.rs**：在 `room_create` 插入 `rooms` 前，先
   `SELECT EXISTS(SELECT 1 FROM conversations WHERE id = ?)` 校验会话存在性；
   若不存在则提前返回明确语义错误（符合 C2 零回退，不用 DB 晦涩 FK 错误替代）。
   同时移除临时诊断日志，保留一条简洁 reject 日志。

3. **SessionSidebar.tsx**：新增 `isGuest?: boolean` prop；「关闭房间」按钮的显示条件
   由 `session.roomStatus === 'open'` 改为 `session.roomStatus === 'open' && !props.isGuest`；
   房客态（open 但 isGuest）显示只读提示「房客模式（不可关闭房间）」而非按钮。

4. **App.tsx**：`DesktopViewProps` 新增 `isGuest?: boolean`；`App()` 向 `AnimatedDesktopView`
   传入 `isGuest={roomClientSession()?.conversation.id === selectedConversationId()}`；
   `AnimatedDesktopView` 内 `SessionSidebar` 接收 `props.isGuest`。

5. 回滚之前为定位 787 添加的临时诊断日志（rooms.rs / network/mod.rs / NewChatModal.tsx）。

## 2. 改动动机

- 问题 1 直接阻断房客加入（context snapshot 构建失败，房客拿不到完整上下文）。
- 问题 2 是权限越界：房客不应能关闭房主房间，原逻辑仅按房间状态判断，导致房客看到
  危险操作按钮，点击会触发 `roomClose` 影响房主与其他玩家。
- 问题 3 是防御性加固：即使未来出现孤儿 conversation_id（例如会话被并发删除），也应返回
  明确错误而非 DB 层 787，符合 C2 零回退约束。

## 3. 约束合规审计表

| 约束 | 合规 | 说明 |
|------|------|------|
| C1 Frontend Render-Only | √ | 前端仅做 UI 条件渲染与 prop 透传，未承担非渲染逻辑；后端校验仍在 Rust 侧 |
| C2 Zero-Fallback Errors | √ | `room_create` 孤儿 id 返回明确错误，未吞异常/未静默回退 |
| C3 Responsiveness | √ | 仅新增一次 O(1) 的 EXISTS 查询与同步 UI 判断，无阻塞 |
| C4 AI UI Isolation | √ | 未涉及 AI 沙箱层 |
| C5 Mobile Frontend Independence | √ | 改动仅触及 PC 前端组件与共享后端；移动端 `src-mobile` 无对应房间 UI（已 grep 确认无 `wb.name`/关闭房间/`isGuest`），未改动移动端，未引入跨端耦合 |
| C6 Project Cache Location | √ | 未写任何文件到系统盘，仅修改源码 |
| C7 PC/Android Coverage | √ | 后端 Rust 为双端共享：`wb.title` 修复与 `room_create` 校验对 Android 房客加入同样生效；房客关闭按钮 UI 仅 PC 存在（移动端无此 UI），属合理范围 |

## 4. 验收记录

### 构建命令与输出
- 后端：`cd src-tauri && cargo build` → 输出 `BACKEND_BUILD_OK`（无 error[]）
- 前端：`npx tsc --noEmit -p tsconfig.json` → 输出 `FRONTEND_TSC_OK`（无 error）

### 预期效果
1. 房客加入房间时不再出现 `no such column: wb.name`，能正常获取 host world book 名称与完整上下文。
2. 房客会话展开后显示「房客模式（不可关闭房间）」，不再出现可点击的「关闭房间」红色按钮；
   房主自己的房间仍正常显示「关闭房间」按钮。
3. 若以不存在的 `conversation_id` 创建房间，前端收到明确错误文案「创建房间失败：会话 N 不存在或已被删除…」，而非 DB 787。

### 检查点
- [ ] 房客加入不报 wb.name 错误（需联机复现）
- [ ] 房客侧无「关闭房间」按钮
- [ ] 房主侧「关闭房间」按钮正常
- [ ] 孤儿 conversation_id 创建房间返回明确错误
