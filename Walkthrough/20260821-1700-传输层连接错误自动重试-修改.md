# 20260821-1700 传输层连接错误自动重试 修改

## 1. 改动摘要
- 文件：`src-tauri/src/services/stream_processor.rs`
- 函数：`execute_provider_http_request`（HTTP 发送站点）
- 改动：`execute_provider_http_request` 的发送逻辑由单次 `.send().map_err(...)?` 改为带传输层重试的 `loop`：
  - 仅对**连接级失败**（`err.is_connect() || err.is_request()`）重试一次（`TRANSPORT_RETRY_LIMIT = 1`）。
  - 失败发生在取得任何响应字节前（`SendRequest` 阶段），重试重发整个请求体是**幂等**的。
  - 死连接被 hyper 在失败后移出连接池，重试必然拿到/新建一条活连接。
  - 重试日志：`[chat] HTTP 连接级失败，传输层自动重试 (第 N 次): ...`
  - 保留上一轮提交 `6355dea` 的 `cause=...` 增强报错文本。
  - 非连接级错误（超时/解码/body/重定向）**不重试**，直接返回原错误，避免无意义等待。

## 2. 改动动机
- 现象：向 NVIDIA 自定义 provider（`https://integrate.api.nvidia.com/v1/chat/completions`）发请求偶发 `HTTP 请求发送失败 ... | connect=false request=true ... | cause=client error (SendRequest) <- connection error`，且 `auto_retry disabled` 时首败即终止，用户完全拿不到回复。
- 根因（已用 curl 大包实测定案）：应用用全局单例 `shared_permissive_http_client()` 的 keep-alive 连接池，复用了 Akamai/NVIDIA 边缘已超时关闭的空闲连接 → 发送阶段 `connection error`。网络与本机 curl 直连均正常（curl 120KB authed POST 拿 401），属纯软件侧连接池问题，非网络故障。
- 设计取舍：禁用连接池（`pool_max_idle_per_host(0)`）会让 agent 模式每次握手累积延迟；改为**保留池 + 传输层连接错误重试一次**，兼顾稀疏聊天（自愈死连接）与密集 agent 模式（正常复用池保速）。该重试独立于用户的内容级 `auto_retry` 开关（撞死连接是基础设施故障，不应被用户的内容重试开关阻断）。
