# Walkthrough: 蓝图内容模板渲染与开场消息接通 minijinja

- 修改类型：修改
- 日期：2026-07-23
- 关联 Spec：`.trae/specs/blueprint-content-template-rendering/spec.md`（状态：已批准，已实现）
- 关联任务：编译期统一文本渲染层（蓝图节点 content + 角色卡开场消息）

## 1. 改动摘要

把「系统创作、可持久化、可能引用运行时值的文本」统一接入既有 minijinja 渲染器 `render_prompt_template`（`prompt_compiler.rs:1660`），在 `compile_prompt` 时统一渲染。落地两个站点：

- **蓝图 Prompt 节点 content**：`prompt_compiler.rs:631-645`。在 `CompiledBlock` 转 `PromptBlock` 前，对每个 `content` 调用 `render_prompt_template`。渲染与转换分离——`compiled_block_to_prompt_block` 保持纯转换不变。
- **角色卡开场消息**：`ensure_opening_in_history`（`prompt_compiler.rs:2203-2249`）签名新增 `render_context: &PromptTemplateRenderContext`，返回类型改为 `Result<(), String>`；在 `load_opening_block` 返回原始 content 的 block 之后、注入历史之前，对其 `content` 渲染。`compile_prompt` 调用点（`:804-813`）加 `&render_context` 并加 `?`。`load_opening_block` 本身不改。
- **单元测试**：`prompt_compiler.rs:2883-2977` 新增 `sample_render_context()` 辅助与 4 个测试，覆盖 D1/D2/D3/D6。

涉及文件：
- `src-tauri/src/services/prompt_compiler.rs`（蓝图 transform、开场渲染、测试）
- `.trae/specs/blueprint-content-template-rendering/spec.md`（状态更新为已实现）

未改动：`blueprint_executor.rs`（执行器仍纯内存、无模板概念）、`conversations.rs`（开场仍原样落库）、前端（PC/移动均零改动）、`BlueprintExecutionContext`。

## 2. 改动动机

- 蓝图 Prompt 节点 `content` 此前在编译期原样透传，作者无法引用运行时值（角色名/玩家名）。
- 从 SillyTavern 导入的 `{{char}}`/`{{user}}` 宏原样发给 LLM 变字面垃圾。
- 角色卡开场消息走独立路径（`load_opening_block` + `conversations.rs` 原样落库）同样不渲染，作者写的用户占位符会变成字面垃圾。
- 把内容模板层从「蓝图专属」升级为「编译期统一文本渲染层」，蓝图节点与开场消息获得一致运行时插值能力，并消除「蓝图 vs 模板」互斥。

决策（用户 2026-07-23 拍板，详见 spec §5）：
- D1 总是渲染（无 `{{ }}` 文本 minijinja 原样透传，零副作用）。
- D2 未定义变量 Strict 报错，无静默回退（C2）。
- D3 `{{user}}`/`<user>` → `player_character.name`。
- D4 不开放 `{% %}` 控制流。
- D5 运行时只认 minijinja，ST 方言在导入层翻译。
- D6 开场归属限 AI 角色卡，可引用 `character.*` 与 `player_character.name`；开场时刻无用户轮次，不应引用 `current_user.content`。

## 3. 约束合规审计表

| 约束 | 合规 | 说明 |
|------|------|------|
| C1 Frontend Render-Only | √ | 纯后端编译逻辑，前端零改动 |
| C2 Zero-Fallback Errors | √ | 渲染失败 → `format!("...: template render failed: {err}")` → 作为 compile 错误上抛 → UI 可见；未知变量 Strict 报错，无静默回退；DB 加载错误保持 best-effort（非致命），与模板渲染错误显式分层 |
| C3 Responsiveness | √ | 渲染为同步字符串模板，无 IO、无阻塞；每轮 compile 一次 |
| C4 AI UI Isolation | √ | 不涉及 AI 沙箱层 |
| C5 Mobile Frontend Independence | √ | 后端改动，前端（PC/移动）均无改动，天然双端覆盖 |
| C6 Project Cache Location | √ | 无缓存写入 |
| C7 PC/Android Coverage | √ | 后端 command 共享，双端自动覆盖；本变更无前端 UI |

错误分层设计（C2 关键）：`ensure_opening_in_history` 对 DB 加载错误保持 best-effort（`Err → log + return Ok`），但模板渲染错误通过 `?` 上抛为编译错误——避免渲染失败被 best-effort 静默吞掉。

## 5. 已知限制 / 后续

- 不提供 random/dice 蓝图节点（运行时随机/骰子由用户单独设计，需注册 minijinja 自定义函数 `rand_choice`/`dice`）。
- ST2NV-Converter 的 ST 宏 → minijinja 翻译是独立 Companion 任务（见 spec §7）；不翻译则导入蓝图里的 `{{char}}` 在 D2 下编译期报错（预期行为，非缺陷）。
- `{% %}` 控制流未文档化，待后续决定是否正式开放。
- `<user>` 等 ST 尖括号方言不是 minijinja 语法，D2 拦不住，必须由导入层翻译（本变更不负责）。
