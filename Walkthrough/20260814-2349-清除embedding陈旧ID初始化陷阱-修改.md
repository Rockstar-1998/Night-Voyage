# 20260814-2349-清除embedding陈旧ID初始化陷阱-修改

## 1. 改动摘要

清除 `src/components/RightDrawer.tsx` 中 embedding 绑定的陈旧 ID 初始化陷阱（即此前方案 A/C 遗留项：打开层状态抽屉时，embedding 下拉框被初始化为一个可能已失效/悬空的 provider id）。

- **`createMemo` 同步逻辑（原 Line 208）**：原代码
  `setBindingEmbeddingProviderId(props.selectedEmbeddingProviderId != null ? String(props.selectedEmbeddingProviderId) : '')`
  会无条件把 `selectedEmbeddingProviderId` 写进下拉框。若该 id 指向已删除的 provider（如残留的 `0`），下拉框会带出一个没有对应 `<option>` 的脏值，并在保存时可能把悬空引用重新写回后端。
  改为两段式守卫：仅当 `props.memoryMode === 'mem0'` **且** 该 id 真实存在于 `embeddingProviders()`（purpose=embedding 的档案列表）时才采用 `String(id)`，否则初始化为 `''`（下拉框"保持当前"项）。
- **`selectedEmbeddingProviderLabel` memo（原 Line 115-118）**：原先对"id 存在但找不到 provider"的悬空情况返回 `当前会话已绑定 Embedding 档案 #${providerId}`（显示幽灵 #id）。改为统一返回 `当前会话未绑定 Embedding 档案。`，与初始化守卫保持一致，不再向用户展示不存在的绑定。

## 2. 改动动机

方案 A/C 已从后端根治悬空引用，但前端仍存在一个**表象层**的同类缺陷：抽屉打开时把"数据库里可能残留的失效 id"直接塞进受控下拉框。这违反 AGENTS.md 的同一底层原则（L121「无效状态不可表达」/ L120 组合优于继承）——UI 不应呈现一个在可选集中根本不存在的选项。同时它也是此前用户报错体验的最后一处"脏值露脸"入口。

修复策略与后端一致：**按 memory_mode 分流 + 仅采纳真实存在的引用**。前端只做"展示层可呈现性"判断（该 id 是否在我能列出的 embedding 档案里），不做任何业务校验——业务逻辑仍由后端负责（C1 边界保持）。
