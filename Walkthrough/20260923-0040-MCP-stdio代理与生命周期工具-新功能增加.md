## 改动摘要

| 文件 | 改动 |
|---|---|
| `scripts/nv_mcp_stdio_proxy.mjs`（新增） | stdio MCP 代理：8 个业务工具透传 + 3 个生命周期监督工具 |

## 改动动机

http 型 MCP 连接器只有在 WorkBuddy 会话启动那一刻客户端已在运行时才能完成握手；客户端晚起，工具清单永远进不了会话的 deferred 工具索引，且会话中途信任/刷新连接器无效。stdio 代理由宿主 spawn，存活与客户端无关，任何会话都能拿到工具清单；同时把"启动/关闭/重启客户端"这类只有外部监督者能做的事收进代理层，作为 `nv_app_start` / `nv_app_stop` / `nv_app_restart` 三个工具。

## 运作机制

- 传输：stdin/stdout 按行分隔 JSON-RPC 2.0（MCP stdio）。`initialize` / `tools/list` / `tools/call` / `ping`。
- 业务工具透传：代理用 `node:http`（不走系统代理）POST `127.0.0.1:55287/mcp`，带 `X-NV-Token`（读 `D:\software_cache\night-voyage-mcp.token`）。客户端侧的业务错误（`isError`）原样透传，不改写不吞错。
- 未启动语义：原始 socket 探测端点；客户端未运行时 8 个业务工具统一返回「程序未启动」（`isError: true`），不降级、不伪造。
- 生命周期：`nv_app_start` 以 `.cache\instances\instance-<a|b>\night-voyage.exe` 为目标、**exe 同目录为 cwd** 启动（detached + unref），轮询端点就绪（上限 90s）；`nv_app_stop` 先 `taskkill /IM` 再超时强杀；`nv_app_restart` = stop + start。
- 串行队列：请求按到达顺序逐条处理，避免生命周期工具与业务工具并发打到正在退出的进程上；stdin 关闭时等待在途请求落地再退出。
- `taskkill` 回显为 GBK，按 `gb18030` 解码。

## 已知限制与后续待办

- 沙箱 Bash 内 `node.exe` 被安全策略黑名单拦截（`PROGRAM BLOCKED BY SECURITY POLICY`）：**只影响沙箱内直接跑 node**，宿主 spawn 的代理不受影响。沙箱内需要驱动端点时用集成工具，不要跑 node/python。
- 代理启动的客户端依赖代理进程存活（宿主会话内稳定）；宿主退出后客户端是否存活未验证。
- `.trae/specs/nv-mcp-control-tools/spec.md` 仍为旧 7 工具/直连 http 的描述，与现状（8+3 工具、stdio 代理）不一致，待用户决策后重写或废弃。
- 既有缺陷 X01（`arguments_json` 吞解析错误）、X02（空背包 `-0.0`）、`write_text` 不落库仍原样存在，等决策。
