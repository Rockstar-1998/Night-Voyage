## 改动摘要

### 1. `src-tauri/src/services/agent/graph_orchestrator.rs`（尾锚读初稿静默回退）

- 原：`execute_orchestration_plan` 的 `NodeInput::AnchorBlackout` 臂以 `scratchpad.read_text("draft").unwrap_or_else(|_| draft.clone())` 读取初稿，失败时静默用本地缓存变量 `draft` 续跑。
- 改：工作区初稿为唯一真相源——`read_text` 失败经 `map_err` 带 stage 上下文（「尾锚节点读取工作区初稿失败（stage=…）：…」）以 `?` 冒泡为显性错误；同时删除本地 `draft` 缓存变量（其唯一读取方就是该回退点，保留它等于保留第二真相源）。
- 取舍：所在函数签名本就返回 `Result<String, String>`，错误通道现成，故按首选方案冒泡，不取「记日志后回退」。语义核查：本地 `draft` 仅在入口节点臂赋值，而该臂同时写工作区 `draft` 键——键缺失时本地值必为空串，即旧回退在真实失败场景下等价于「拿空初稿算尾锚静默续跑」，是实打实的静默降级，改硬错无合法流程损失。
- 配套更正：工单 03 Walkthrough（`20261111-0047-…`）的 C2 行原误标 ✓，已在该文件末尾追加「审查修正（2026-11-11）」一节更正（原文不篡改）。

### 2. `src-tauri/src/services/agent/cycle.rs`（`_ => {}` 吞未知块类型）

- 原：`parse_step_response` 的 Anthropic 臂以字符串 block type 匹配，`_ => {}` 无声丢弃未知块。
- 改：显式分 `Some(other)` 与 `None` 两臂，均经项目统一诊断通道 `crate::dbg_eprintln!` 记录（未知类型记类型名、无 type 字段单独记）后跳过该块；「忽略」从此是有日志的显式行为。
- 取舍：scrutinee 是提供商 JSON 的字符串字段、取值域开放（thinking、server_tool_use 等会随提供商演进新增），无法穷尽枚举，故不取「未知即硬错」——正文/工具调用的解析契约不因不消费的块类型而失败，这与同函数对结构性缺失（缺 content/id/name）硬错的区别在于：前者是开放域的已知无害信息，后者是本运行器必需字段。日志通道说明：本 crate 未引入 `tracing`/`log` 依赖，全仓诊断统一走 `dbg_eprintln!`（同模块 `graph_orchestrator.rs`、服务层多处先例），本次沿用仓库惯例，未为单点日志新引依赖。

### 3. `src-tauri/src/services/blueprint_codec.rs`（schema 伪装 + 裸默认放行）

- `:135` 导出侧：原 `serde_json::from_str::<Value>(schema_raw).unwrap_or_else(|_| json!(schema_raw))` 在 `parameters_schema` 解析失败时把损坏原文伪装成字符串型 parameters 导出。改：`map_err` 带工具名上下文（「工具 X 的 parameters_schema 不是合法 JSON，无法导出为 .nv.ts：…」）以 `?` 冒泡，导出显性失败。所在函数 `export_graph_to_code` 本就返回 `Result<String, String>`，无签名变更。
- `:359` 导入侧：原 `pos.map(…).unwrap_or(true)` 对缺失 position 的节点无声按「未定位」处理。取舍结论：**保留默认语义、改为显式命名**。理由：导入契约中「无 position」就是「待自动布局」的表达而非数据损坏——同文件 `take_position` 对缺失 position 的既有处理（赋占位原点并标记 needs_layout）证明这是契约内状态；若改硬错，全部无坐标的历史代码预设将不可导入，与工单 05 的无损往返目标相悖。落地方式：抽出具名函数 `is_default_origin_position(Option<&Value>) -> bool`，带文档注释写明该默认的契约依据，并由单元测试固定四种输入行为，裸 `unwrap_or(true)` 消除。
