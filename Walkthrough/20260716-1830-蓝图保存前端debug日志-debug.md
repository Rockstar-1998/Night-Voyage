# 蓝图保存前端 debug 日志

## 改动摘要

| 文件 | 操作 | 说明 |
|------|------|------|
| `src/lib/debug/blueprintSaveDebug.ts` | 新增 | 隔离的前端 debug 模块，4 个日志函数覆盖保存/加载/更新链路 |
| `src/components/blueprint/BlueprintEditor.tsx` | 修改 | 在 handleUpdateNode / handleSave / onMount 加载处加 debug 调用 |

## 改动动机

后端日志显示保存链路完全成功（`[preset-save] success`，`blueprint_graph_len=583`，`tx: committed`），但用户报告"保存后重新打开内容丢失"。

后端写入已确认成功，问题定位转移到前端：
1. **保存的是否是旧内容**（用户编辑没进入 graph store）→ 重新打开自然是旧的
2. **保存的是新内容，但加载时读到旧数据**→ 数据库读取问题

需要在前端加 debug 日志确认：
- 用户编辑是否触发 `handleUpdateNode`（`logUpdate`）
- 保存时序列化的 graph 内容是什么（`logSaveStart`）
- 后端返回的更新后的 graph 内容是什么（`logSaveDone`）
- 重新打开时加载的 graph 内容是什么（`logLoad`）

对比这四个日志即可定位问题根因。

## debug 函数说明

| 函数 | 调用位置 | 输出 |
|------|----------|------|
| `logUpdate(nodeId, updates)` | `handleUpdateNode` | 用户编辑触发的 node id 和 updates 内容 |
| `logSaveStart(json)` | `handleSave` 序列化后 | 保存到后端的 graph JSON 前 300 字符 |
| `logSaveDone(updatedGraph)` | `handleSave` 后端返回后 | 后端返回的更新后的 blueprint_graph 前 300 字符 |
| `logLoad(rawGraph)` | `onMount` 加载时 | 从后端加载的 blueprint_graph 前 300 字符 |

所有日志前缀 `[bp-debug]`，便于在浏览器控制台过滤。

## 约束合规审计表

| 约束 | 合规 | 说明 |
|------|------|------|
| C1 Frontend Render-Only | √ | debug 日志只记录不调用后端 |
| C2 Zero-Fallback Errors | √ | debug 日志只记录不影响业务逻辑 |
| C3 Responsiveness | √ | console.log 是同步但极快，不影响响应 |
| C4 AI UI Isolation | √ | 不涉及 |
| C5 Mobile Frontend Independence | √ | PC 独立 debug 模块，移动端未改 |
| C6 Project Cache Location | √ | 不涉及缓存 |
| C7 PC/Android Coverage | √ | 仅为 debug 日志，双端覆盖不适用 |

### 预期效果

用户重新打开蓝图编辑器，编辑节点，点击保存，然后关闭重新打开。浏览器控制台会输出：

```
[bp-debug] load raw_len=XXX {"version":2,"nodes":[...
[bp-debug] update nodeId=xxx { type: 'constant', config: { label: 'xxx' ... } }
[bp-debug] save-start json_len=XXX {"version":2,"nodes":[...
[bp-debug] save-done updated_graph_len=XXX {"version":2,"nodes":[...
```

对比 `save-start` 和 `save-done` 的内容可以确认后端是否正确写入了用户编辑的内容。
对比 `save-done` 和下次打开的 `load` 内容可以确认数据库读取是否正确。
