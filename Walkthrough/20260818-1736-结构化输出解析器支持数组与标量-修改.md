# 修改：结构化输出流式解析器支持数组/数字/布尔/null 值

## 1. 改动摘要

### 根因
`src-tauri/src/services/structured_output_parser.rs` 的 `ExpectValue` 状态机（原 `Phase::InObjectValue` 路径）只识别 `"`（字符串）和 `{`（对象）两种值起始符。当 schema 中存在数组字段（如 `todo_list: []`、`options: []`）或标量字段（数字、`true`/`false`/`null`）时，状态机命中 `_ =>` 通配臂，先 `push(ParseError)` 再 `return` —— **且不推进 `pos`**。解析器永久卡死在 `ExpectValue`，后续每次 `feed` 都重复触发同一错误；最终 `finish()` 因 `phase != Complete` 返回 `Err`，被 `stream_processor.rs` 误判为「模型未返回合法 JSON」而错误切入兼容模式，把本应保留的结构化字段整体塞进 `narrative`。

模型实际返回的是合法 JSON 且符合 schema（见调试日志 `agent_req_1787042399_...json`：
`{"thinking":"","status_bar":{},"todo_list":[],"options":[],"narrative":"..."}`），属**软件解析器缺陷（false positive）**，非回复体问题。

### 改动文件与内容
- **`src-tauri/src/services/structured_output_parser.rs`**（核心修复）
  - `Phase` 枚举：将 `InObjectValue` 泛型化为 `InContainerValue`，新增 `InScalarValue`。
  - `ExpectValue` 臂：新增对 `[`（数组）、`-`/`0-9`（数字）、`t`/`f`/`n`（布尔/null）的处理，分别进入 `InContainerValue` / `InScalarValue`；`_ =>` 仅对真正的非法字符报错。
  - `InContainerValue` 臂：深度计数同时追踪 `{`/`}` 与 `[`/`]`，闭合时对 `object_raw` 调用 `serde_json::from_str::<Value>`：
    - 若为 `Value::Object` → 复用既有 `ObjectFieldComplete` 事件 + 写入 `fields`（行为不变）；
    - 否则（数组/数字/布尔/null）→ 直接写入 `fields`，不触发 ParseError。
  - 新增辅助方法 `complete_container_value` / `complete_scalar_value`（解析并落库，解析失败仅记 `ParseError` 事件并继续推进，不再卡死）。
  - 测试模块新增 7 个用例：`test_empty_array_field`、`test_array_of_objects_field`、`test_nested_array_inside_object`、`test_scalar_fields_number_bool_null`、`test_negative_and_float_number`、`test_real_debug_log_shape_no_compat_mode`、`test_incremental_array_feed`。
- **`src-tauri/src/services/stream_processor.rs`**（文案修正）
  - 两处兼容模式提示文案由「模型回复未返回合法 JSON」改为准确描述「流式解析未完成或结构非法」。仅在 `finish()` 真正失败时触发，不再对合法 JSON 误报。

### 构建解阻塞增补（重要，需用户知悉）

## 2. 改动动机
消除「合法结构化 JSON 被错误判定为兼容模式」的 false positive，避免数组/标量字段被整体吞入 `narrative`、结构化能力名存实亡。修复同时纠正了误导性的兼容模式提示文案。

## 3. 约束合规审计表

| 约束 | 合规 | 说明 |
|------|------|------|
| C1 Frontend Render-Only | √ | 纯后端 Rust 解析器改动，未将任何逻辑移至前端 |
| C2 Zero-Fallback Errors | √ | 合法数组/标量不再误报；真实解析失败仍经 `ParseError` 事件 + `finish()` 错误上升为兼容模式（文案已修正为准确描述），无静默回退 |
| C3 Responsiveness | √ | 增量流式解析逻辑不变，无阻塞、无新主线程负担 |
| C4 AI UI Isolation | √ | 未触碰 AI 沙箱/宿主隔离层 |
| C5 Mobile Frontend Independence | √ | 无前端改动，`src` 与 `src-mobile` 零耦合 |
| C6 Project Cache Location | √ | 无新增缓存写入 |
| C7 PC/Android Coverage | √ | 后端共享解析器；两处流式入口（`stream_processor.rs` 两函数）均复用同一 `StructuredOutputParser`，无单端后门 |

组合/惯用法：未引入 OOP 反模式；`Phase` 状态机 `match` 穷尽（无 `_ =>` 吞未知变体）；容器深度计数与 `serde_json` 复用，无裸 `unwrap`/新增 bool 标志位。

## 5. 已知限制或后续待办
- 数组/数字/布尔/null 字段目前**仅在 `finish()` 时整段落库**，不发送增量流式事件（对象走 `ObjectFieldDelta`/`ObjectFieldComplete`、字符串走 `StringFieldDelta`）。若前端需要对数组做逐元素流式渲染，需新增 `ArrayFieldDelta`/`ScalarFieldComplete` 事件类型并在 `stream_processor.rs` 消费——当前为数据正确性优先，流式增量属增强项，未在此次范围。
- 用户 WIP 中 `SchemaFieldConfig` 三字段的构造点补全（见 §1 解阻塞增补）需用户在提交其 WIP 时确认默认值。
- push 可能因出网 TLS 握手失败被拒（PUSH_EXIT=128），属已知环境限制，不影响本地提交与验证。
