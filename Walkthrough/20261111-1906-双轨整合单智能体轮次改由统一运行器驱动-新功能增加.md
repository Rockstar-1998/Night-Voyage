# 双轨整合：生产单智能体轮次改由 AgentCycleRuntime 驱动（工单 01-S1 / spec 解法 1）

## 改动动机

工单 01 的 `AgentCycleRuntime` 此前在生产路径零调用：生产单智能体轮次实际由一条跨任务递归链驱动——`stream_llm_response`（一跳流式请求）→ `ChatService::dispatch_tool_calls`（批量执行 + 回注）→ `submit_tool_results`（落盘 + 创建新轮 + `spawn_stream_task` 续跳），步长熔断是 `submit_tool_results` 里的 `MAX_TOOL_ROUNDS_PER_TURN = 5` 计数，短路则根本不存在（图盖章 `max_steps = 1` 的预设仍会发起第 2 次 API 调用）。蓝图 StepBudget 盖章与运行器只是「写好了但没接上」。本阶段把这条链整合为运行器驱动的单任务循环：步进 / 短路 / 熔断只在运行器一处判定，流式细节仍只在 `stream_processor` 一处实现。

## 设计决策（codebase-design）

### Seam 与 Adapter

`cycle.rs` 的两个 trait（`AgentStepProvider` / `AgentToolExecutor`）就是预留 Seam，此前只有 mock 与非流式 `HttpStepProvider` 两个 Adapter。本阶段在新增模块 `services/agent/stream_cycle.rs` 补上流式 Adapter，使该 Seam 具备「两个生产 Adapter 才算真 seam」的完整形态：

- **`StreamingStepProvider<B: StreamingStepBackend>`**（`AgentStepProvider` 的 Adapter）：后端执行「一跳流式请求」。生产 backend 是 `stream_processor::DbStreamingStepBackend`，包住既有的整跳流式管线（见下）；测试 backend 是脚本化响应序列。
- **`StreamingToolExecutor<B: StreamingToolBackend>`**（`AgentToolExecutor` 的 Adapter）：后端执行一次本地工具调用。生产 backend 是 `stream_processor::DbStreamingToolBackend`，包住 `execute_tool_call_with_plan` 全链（白名单 → 契约 → 门禁 → 容器落盘）+ 时序泳道回执发射 + 回执按序收集；测试 backend 是脚本化记录器。

Adapter 自身不持有任何步进 / 短路 / 熔断逻辑，是薄包层；复杂度（循环政策）集中在运行器（Locality），测试经 Adapter 接缝即可验证短路计数、多步跑完与旁白保底（interface 即测试面）。

### 接缝契约：提示词物化归 backend

`AgentStepProvider::run_step` 的 `system_blocks` / `history` / `tools` 参数是为内存型调用方（如 `HttpStepProvider`）准备的物化视图。生产流式 backend 不消费这三个参数，理由是生产环境的历史权威物化在 DB 一侧：每一跳由 `prompt_compiler` 按最新落盘历史重新编译——该历史已经包含上一跳回注的 ToolResult、世界书触发、记忆检索、Schema 保持期裁剪与 Token 预算裁剪，全部是逐跳动态状态，无法由运行器内存中的 `Vec<LlmMessage>` 忠实替代。强行以内存历史替代 DB 编译会实质改变提示词语义（工单 02 行为之外的新回归面）。因此接缝契约明确为：backend 负责逐跳物化提示词并执行恰好一次 API 往返；运行器负责全部循环政策（走几步、何时短路、何时熔断），backend 无权自行续跳或截断。`AgentCycleConfig` 的装配值（system 块、用户输入、工具白名单）取自与第一跳执行完全相同的一次预检编译，是真实值而非占位。

### 一跳 = 一个 DB 轮次（落盘模型不变）

整合不改变落盘模型：第 k 跳仍是独立的 DB round + 助手消息，逐跳的重试快照种子、轮次状态快照基线（工单 04）、结构化输出解析、Abort 巡检与旧链逐项等价。变化只在驱动方式：第 k+1 跳不再由 `submit_tool_results` 内部 `spawn_stream_task` 新开任务递归进入，而是由 step backend 在同一任务内链式落盘后直接执行——`chain_previous_step`：上一跳回执 → `fill_fallback_narrative_if_empty` 旁白保底回填 → `ChatService::persist_tool_results_round` 回注落盘创建新轮 → 新轮 `capture_baseline` → 会话坐标切换。原跨任务递归使「一轮对话」散落在多个任务与多套 Nudge/重试状态中；整合后一轮恰好对应一次 `run_cycle` 调用。

### 步长喂入与 None 翻译规则

装配点：`stream_llm_response` 在调用运行器前先经 `DbStreamingStepBackend::prepare_first_step` 预检编译第一跳，步长盖章（阶段 1b 的 `Option` 语义，经本阶段新增的 `PromptCompileResult::step_budget` / `short_circuit_on_first_step` 透传通道从 `BlueprintExecutionResult` 原样到达）由此进入装配层。翻译规则（`stream_cycle::translate_step_budget`，纯函数、全表测试覆盖）：

| 盖章 step_budget | 盖章 short_circuit | 翻译结果 (max_steps, short_circuit) |
|---|---|---|
| `Some(n)` | `Some(b)` | `(n, b)` 原样 |
| `Some(n)` | `None` | `(n, false)`（仅旧载荷可能出现，显式不短路） |
| `None` | 任意 | `(usize::MAX, false)`（命名常量 `UNLIMITED_STEP_BUDGET`：不限制步数、不短路） |

`None` 绝不默默当 1：未声明预算的预设若被截断为单步，与阶段 1b「无声明 = 无限制」的定案相悖。`usize::MAX` 使运行器的熔断判定 `steps_taken >= max_steps` 在任何现实步数下不触发，语义即「不限制」而非某个隐含小默认值。`Some(0)` 不翻译、由运行器自身的配置校验显式硬错（C2）。

终局处理（驱动层）：

- `TextDelivered`：最后一跳产物（正文 + 该跳 db_mappings / HUD 白名单）即整轮产物，交回 `spawn_stream_task` 做禁词校验与轮后任务，与整合前最终跳语义一致；
- `ShortCircuitedWithTools`：以会话收集的回执摘要调用 `fill_fallback_narrative_if_empty` 落盘旁白保底（正文为空时内存产物同步替换为合成旁白，保证 spawn 层校验 / 轮后任务消费的文本与落盘一致），整轮结束——回执不回注、无下一跳，与 spec 单步语义一致；
- `CircuitBreakerTripped`：转为显式错误「Agent 步长预算熔断（已执行 N 步）: 原因」按 spawn 层统一失败路径收尾（C2）。

## 工单 02 行为契约逐项核对表

| 契约 | 整合后实现 | 结论 |
|---|---|---|
| 文本逐块即时发射 | 流式解复用函数 `stream_openai_text_response` / `stream_anthropic_text_response` 本体零改动，仍在 `execute_stream_step` 内按原路径逐块 `flush_text_delta_event` 发射；Adapter 只在整跳返回后向运行器汇报 | 保持 |
| 工具分片不入对白流 | `StreamingToolAccumulator` 静默拼装路径零改动 | 保持 |
| 旁白保底（正文为空 + 有工具执行时本地合成、不发第二次请求） | 多步链：`chain_previous_step` 在回注落盘前调用同一 `fill_fallback_narrative_if_empty`；短路终局：驱动层以同一函数落盘同一合成文案（`short_circuit_narrative` 与落盘共用 `synthesize_fallback_narrative`）；均不发起额外请求 | 保持 |
| `[DONE]` 原子收尾 | `complete_tool_use_turn` 链零改动，仍由流式函数在 `[DONE]` / 自然结束 / `tool_use` 三路统一调用 | 保持 |
| 双 Provider（Anthropic / OpenAI 兼容） | `execute_stream_step` 内按 `provider_kind` 分发原样保留，两条流式通道均成为 Adapter 的一跳 | 保持 |
| 既有 stream 测试 | accumulator / fallback 全部既有测试未改一字、全绿（见验收记录） | 保持 |

补充说明：整合前工具跳的正文会先经其自身 spawn 任务的禁词校验、续跳已 spawn 后父跳再校验，存在续跳与校验竞态；整合后禁词校验只对整轮终稿执行一次（中间跳正文不是终稿），竞态消除。这是行为收敛而非契约回退，校验强度不降（终稿必过门禁，轮后任务在其后）。

## run_multi_agent_round 的终局

保留原名，理由：其职责（多智能体一轮的分发与收尾）未变，改名只制造无意义的符号漂移；函数文档已补终局定位。它不再是第二条执行轨道的论证：

1. 入口分发只剩按 `AgentPipeline` 标签选择编排计划；导演-演员（阶段 2 的 FanOut 图编排）与编剧线（图编排计划执行器）同为图语义计划，`Single` 永不路由到此（误入即显式报错，原有守卫保留）；
2. 内部不含任何步进 / 短路 / 熔断逻辑：仅有终稿落盘、禁词 Nudge 内容门禁重试（内容合规政策，非步长政策）与轮后任务；
3. 单智能体轨道的旧收口点已物理删除：`dispatch_tool_calls` 全仓零引用（已删除），`submit_tool_results` 的 spawn 续跳只剩命令包装（前端 `chat_submit_tool_result` 人工回注入口）一条路径，模型驱动链不再经过它。

循环政策单点性（grep 证据，提交时实测）：短路判定 `short_circuit_on_first_step && steps_taken == 1` 与熔断判定 `steps_taken >= max_steps` 只存在于 `services/agent/cycle.rs:211/219`；生产调用点唯一处 `services/stream_processor.rs` 的 `stream_llm_response` 内 `AgentCycleRuntime::run_cycle(...)` 一行。两处保留的同名概念均非单智能体轮次的步长政策：`chat_service` 的 `MAX_TOOL_ROUNDS_PER_TURN` 现仅为人工回注命令的准入检查（受理一次人工回注前校验既往轮次，包装文档已明示与运行器熔断不叠加）；`subagent.rs` 的 `max_rounds` 是非流式子智能体阶段调用内部的工具轮次上限，服务于多智能体图编排的阶段执行，不在单智能体轮次轨道上——其与运行器的关系属后续阶段议题，本阶段不动以免扩大回归面。

## 已知限制或后续待办

- **熔断时已执行工具的回执不回注**：`CircuitBreakerTripped` 终局下，本跳已执行工具的回执留在会话内未落盘为 tool_result 消息（工具的状态变更已按计划生效），整轮按失败收尾。与整合前上限路径行为一致（旧 `dispatch` 在 `submit` 报错时同样未回注）。如需熔断回执落盘留痕，另开工单设计。
- **Nudge / 自动重试的整轮重跑语义**：spawn 层对终稿的禁词 Nudge 重试与错误自动重试会整轮重跑 `run_cycle`（自第一跳起），含工具重新执行；整合前为逐跳重跑，工具同样会被重执行，风险面同级但粒度变粗。工具计划自身的幂等性仍是最终防线，与现状一致。
- **子智能体内部工具循环未并入运行器**：`subagent.rs::run_subagent_with_tools` 的 `max_rounds` 循环服务于多智能体图编排的非流式阶段调用，本阶段按范围不动；其与运行器的统一属后续议题。
- **C8 实机验收未做**：单步短路的实际 API 调用次数、熔断前端报错呈现、双 Provider 实流行为，需用户回电脑后以 MCP 前台演示验收（本地以脚本化 backend 的调用计数断言替代验证逻辑层）。
- 本提交不含 `Cargo.lock`（本地漂移已还原）、不 push。
