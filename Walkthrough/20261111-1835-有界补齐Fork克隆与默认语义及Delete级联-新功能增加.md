# 有界补齐：Fork 克隆快照、步长默认语义纠正与 Delete 级联

「填补剩余缺失 · 阶段 1（有界补齐）」三项：1a Fork 克隆快照（spec 用户故事 22、§5）、1b 工单 01-2 默认语义纠正（spec §2）、1c 工单 04-4 Delete 中间轮级联（spec §5）。设计判断使用 codebase-design 词汇（Module / Interface / Seam / Adapter / Depth / Leverage / Locality、删除测试、Interface 即测试面）。

## 设计决策

### 1a · 克隆方法放在快照仓储 Module 的 Interface 上

- 快照仓储（`RoundSnapshotRepository`）是唯一知道 `round_snapshots` 表形状、`state_json` 序列化与 `round_index` 来源的 Module。在其 Interface 上新增一个小方法 `clone_snapshot(db, source_conversation_id, source_round_id, target_conversation_id, target_round_id) -> Result<bool, String>`，把「读源基线 → 查目标轮序号 → 写目标轮次」全部收进实现内部（Locality）：复制逻辑的任何修正只发生在一处，调用方不拼复制步骤。
- 删除测试检验：若删掉该方法，Fork 调用方就得自己 load 源快照、查目标轮 `round_index`、序列化并 INSERT——这套细节会在每个分支创建点重复出现，说明该 Module 在挣其 Depth：一个五参数方法换掉整套复制流程（Leverage）。
- Interface 即测试面：克隆的全部行为（往返值、两边独立、无源基线的显式 no-op、目标轮不存在报错）都通过仓储 Interface 以真实 SQLite 内存库测试，不触碰实现内部。
- 语义定版：目标轮已有基线时 INSERT 直接报错（Fork 目标轮必为新建轮次，已有基线说明调用方给错目标，静默覆盖会污染新分支回滚基线，C2）；源轮无基线返回 `false` 的**显式 no-op**——Fork 必须能处理本功能上线前的历史轮次（它们天然无基线），与 `restore` 无基线返回 `false` 的既定语义一致，并有测试锁定，不属于静默回退。
- 接线点修正：任务描述称 Fork 在 `chat_service`，代码事实是 Fork 位于 `commands/conversations.rs::conversations_fork`（逐轮复制消息的命令），故克隆调用接在该命令的逐轮循环内——每个被复制轮次都克隆其基线，被 fork 的目标轮自然包含在内，新分支任意一轮的回滚基线都与源会话一致。

### 1b · Option 化：Interface 影响面论证

- `BlueprintExecutionResult` 的 Interface 此前用 `usize`/`bool` 表达步长，类型本身无法区分「图盖章了 max_steps=1」与「图什么都没说」——无效状态可表达，是自创默认的根源。改为 `Option<usize>` / `Option<bool>` 后，「未盖章即无预算约束」成为类型事实：`None` 是唯一的无声明表达，消费方在类型层面不可能把无声明误读成数值 1。
- 影响面核查（先 grep 全仓定位全部下游消费方）：生产代码中**没有任何消费方读取这两个字段**——`prompt_compiler` 只取 blocks/schema/sampling/tools 等字段，`commands/blueprint.rs` 预览只取 blocks/tools/layout，`agent/cycle.rs` 仅在文档注释中引用字段名。`AgentCycleRuntime` 尚未接入实机聊天路径（既有结论，本阶段不动），故不存在把 `None` 翻译成 `AgentCycleConfig` 的生产装配点。Option 化的全部牵连 = 执行器构造初值、traverse 盖章点、模型字段与 serde、 executor/model 单元测试，外加 cycle.rs 文档注释补明装配约定（`None` 时装配方必须显式决定步长，运行器不设隐含默认）。
- 序列化形状：字段带 `#[serde(default)]`，缺字段的旧载荷反序列化为 `None`；`None` 序列化为 `null`。前端没有任何代码读取执行结果的这两个字段（前端 `step_budget` 引用全部是节点类型与节点 config，与执行结果无关），故不存在跨 IPC 形状被前端依赖的问题。基于以上核查，首选方案（Option 化）成立，不需要退到「保留类型 + 命名默认常量」的次选。
- `StepBudgetConfig` 节点自身的字段默认值（config 缺省时 max_steps=1 / short_circuit=true）是 spec §2 节点配置语义的一部分，本次不动。

### 1c · Delete 级联：走「最接近安全语义 + 三项说明」路线

spec §5 字面要求 Delete「Cascade state rollbacks across all undone/deleted rounds」。代码事实证明字面回滚会破坏数据一致性，按 AGENTS.md 三项格式记录（同步写入工单 04 文件的阶段 1 注记）：

- 风险点：后续轮次的基线是在「被删轮突变已发生」的历史链上捕获的（基线内含被删轮的状态效果），且会话现状态同时含被删轮与后续轮的突变；不存在任何既有快照能表达「去掉被删轮、保留后续轮」的状态。若按字面把现状态回滚到被删轮基线，后续轮（消息仍在、仍可见）的合法突变会被一并抹掉，状态与可见历史不一致；若保留后续轮基线，日后对后续轮 Regenerate/Delete 还原时会把已删轮的效果静默复活。
- 影响范围：`ChatService::delete_message` 的中间轮删除路径与 `round_snapshots` 中被删轮及其后轮次的基线行；后续轮在级联失效后失去快照回滚能力（其 `restore` 显式走无基线路径），现状态与后续轮消息本身不受影响。
- 建议的修正方向：已落地的最接近安全语义为「级联失效而非级联回滚」——删除陈旧基线以杜绝错误复活，并经事件明示失效范围；若未来要实现字面级联回滚，需要为每轮保存可重放的工具突变日志（delta log），删除中间轮时按「基线 + 重放剩余轮次 delta」重建状态，这属于独立工单范围，不在本阶段内。

实现形状：级联逻辑同样收进仓储 Module 的 Interface——`cascade_invalidate_for_deleted_round(db, conversation_id, round_id, round_index) -> Result<u64, String>`（内部依次失效后续基线、删除被删轮自身基线，返回后续失效条数），`chat_service` 只做「最后一轮走既有 restore 路径 / 中间轮走级联失效」的边界分发。调用方明示通道按现有 delete 接口形状做最小扩展：`delete_message` 的 Tauri 返回仍是 `()`，故扩展落在既有事件上——`RoomMessage::MessageDeleted` 与其事件载荷新增 `invalidated_later_snapshots`（前端 camelCase `invalidatedLaterSnapshots`），PC 端 TS 类型同步加字段；移动端目前未监听该事件，无对应类型可改，后端事件为双端共享同一通道。

## 改动动机

- 1a：工单 04 落地时 Fork 路径未克隆快照，新分支轮次没有任何回滚基线，在新分支对被 fork 轮执行 Regenerate/Delete 时 restore 恒为无基线，spec 用户故事 22 未兑现。
- 1b：执行器对无 StepBudget 节点的图预置 `step_budget: 1, short_circuit: true`，是 spec §2 没有的自创默认——图未声明预算却被强制单步+短路，与「预算只能由节点物理盖章」的架构定义冲突（工单 01 审查遗留项 01-2）。
- 1c：工单 04 的 Delete 中间轮只删自身快照记录，后续轮的陈旧基线（含已删轮效果）被保留，构成日后还原时静默复活已删数据的隐患；且调用方无从知道级联范围。spec §5 的级联要求需要以数据一致性允许的最接近形式兑现。

## 已知限制或后续待办

- 1c 为「级联失效」而非 spec §5 字面「级联回滚」：被级联失效的后续轮失去快照回滚基线（restore 走显式无基线路径）；现状态中被删轮的历史突变无法单独剥离。字面级联需每轮 delta 重放日志，属独立工单（见工单 04 注记三项格式）。
- `conversations_fork` 本身不复制 `session_states` 当前状态行（本阶段之前即如此，本阶段范围只补快照基线克隆，未扩围）；新分支的当前状态起点行为维持现状，待后续阶段一并评估。
- `AgentCycleRuntime` 仍未接入实机聊天路径（工单 01 审查既有发现），1b 的 `None` 装配约定目前只落在文档与类型上，无生产装配点可改；接入时必须按该约定显式装配。
- 前端 App.tsx 对 `invalidatedLaterSnapshots` 目前仅有类型承接，未做 UI 提示文案；如需用户可见提示（如「已使后续 N 轮的回滚基线失效」），另开前端小工单。
- 本机 `src-tauri/Cargo.lock` 因 MEM0 行为垫片在构建时发生漂移，已按约定还原，未进本次提交。
