## 2. 改动动机

**要解决的问题**：9/18 遗留的验收阻塞——现场演示真实客户端时，代理侧缺少一条**受控、可审计、直连真实后端**的操作通道。此前存在的 `mcp-test-server` 是与 Rust 后端并行的 JS 再实现（自写门禁与负重、不调后端、不读写真实库、并生成合成截图），对真实应用零证伪力，已被认定必须清除；清除后代理侧再无任何合规通道操作真实应用，导致查证只能靠旁路手写脚本——而旁路脚本既不可审计，也正是 9/18 数据被写坏的来源。

**为什么是"应用内端点"而不是"独立进程直连 SQLite"**：`agent_runtime::execute_tool_call` 需 `&AppHandle` 才能调用 `broadcast_hud_patch`，而后者走 `app.emit(..)`，**只能由运行中的后端进程内部发出**。独立进程直连库能够改数据，但改完运行中的界面毫无感知——那不是现场演示。形态因此取本机既有 `claireon`（UE 编辑器 `127.0.0.1:55286`）与 `unity`（`127.0.0.1:8080`）的同构做法：**GUI 应用自监听本地 MCP 端点**。

**为什么用 hyper 而非 axum**：`Cargo.lock` 中 `hyper 1.10.1` / `hyper-util 0.1.20` / `http-body-util 0.1.3` / `bytes 1.11.1` 已作为 Tauri 传递依赖存在。将其提升为直接依赖并开启 `server` / `http1` feature，**不引入任何新的 crate 版本线**；引入 axum 则会带来 `matchit` / `sync_wrapper` / `serde_path_to_error` / `mime` / `tower-layer` 等一整套新依赖。HTTP 语义仍由工业级实现承担，不是手写协议栈。

## 3. 工具清单（全部直调真实服务或真实库）

| 工具 | 真实调用目标 |
|------|--------------|
| `nv_db_info` | `db::resolve_db_path` + `conversations`/`messages`/`session_states` 行数 |
| `nv_conversations_list` | `SELECT id, character_id, title, created_at, updated_at FROM conversations` |
| `nv_session_state_raw` | `session_states.state_json` 原始字符串与长度，不解析不修补 |
| `nv_session_state_get` | `agent_runtime::load_session_state`（与前端 `session_game_state_get` 同一条路径） |
| `nv_tool_call_execute` | `agent_runtime::execute_tool_call`（门禁 + 持久化 + `broadcast_hud_patch`） |
| `nv_session_state_reset` | `agent_runtime::reset_session_state` + `broadcast_hud_patch` |
| `nv_messages_list` | `SELECT id, role, created_at, length(content), is_swipe, swipe_index FROM messages` |

`nv_session_state_reset` 是在准备演示路径时发现的**能力缺口补项**：`execute_tool_call` 入口第一步即 `load_session_state`，对不符契约的存量数据会在加载阶段失败，因此前述任何工具都无法修复坏数据。reset 经真实 service 由 serde 生成字段名必然合法的状态，是修复存量坏数据的唯一合规路径（不手写 JSON 塞库）。

## 4. 约束合规审计表

| 约束 | 合规 | 说明 |
|------|------|------|
| C1 Frontend Render-Only | √ | 逻辑全在 Rust 后端；端点是后端的外部入口，不是 Tauri command，前端零参与、零改动 |
| C2 Zero-Fallback Errors | √ | 工具处理器返回 `Result<String, String>`，无 `unwrap_or` 默认成功、无 `.ok()` 吞错；`nv_session_state_get` 对坏数据原样上抛 `isError:true`；响应序列化失败返回显式错误体而非空响应 |
| C3 Responsiveness | √ | 监听在 `tauri::async_runtime` 独立任务；每连接 `tokio::spawn`；不触碰 UI 线程与渲染路径 |
| C4 AI UI Isolation | √ | 不生成、不注入任何 UI；不触碰 iframe/Shadow DOM 边界 |
| C5 Mobile Frontend Independence | √ | 前端零改动，`src/` 与 `src-mobile/` 均未涉及 |
| C6 Project Cache Location | √ | 令牌落 `D:\software_cache\night-voyage-mcp.token`；构建日志落 `D:\software_cache`；未向系统盘写缓存 |
| C7 PC/Android Coverage | √ | 端点定位为**开发期诊断通道**而非产品功能，故刻意只在 `all(desktop, debug_assertions)` 存在；Android 构建经 cfg 完整剥离，不存在"为单端开后门" |

无 `×` 项，无需例外登记。

## 6. 已知限制与后续待办

1. **未验证**：`mcp.json` 的 `type: http` 连接器是否支持自定义 `headers`。若不支持，`X-NV-Token` 无法随连接器下发而返回 401；兜底为直接 HTTP 调用同一端点（与既有 Claireon 兜底同构，协议与端点一致）。
2. 首批 7 个工具覆盖"库 → 会话状态（读原始/读解析/重置）→ 消息 → ToolCall 执行"主链；蓝图编译链路（`preview_blueprint_with_session`）、mem0 记忆检索、联机房间状态尚未暴露，按调试需要滚动新增。
3. JSON-RPC 批量（数组）载荷与 SSE 流式响应不在支持范围，遇到时显式报错，不静默丢弃。
4. `agent_runtime.rs:88-89` 的第三处 C2 吞错（`arguments_json` 解析 `unwrap_or(空对象)`）仍未修——该处改动需连带前端调试抽屉的空参数入口一起设计，属独立待办。
