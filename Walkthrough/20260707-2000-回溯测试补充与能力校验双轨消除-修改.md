# 回溯功能单元测试补充 与 能力校验双轨消除

## 1. 改动摘要

本次改动是 `capability-matrix-completion` spec 的收尾工作，解决两个验证遗留问题：
（A）回溯功能无专用单元测试；（B）`capability_guard.rs` 同时存在新旧两套能力校验 API。

### 涉及文件

| 文件 | 改动类型 | 说明 |
|------|----------|------|
| `src-tauri/src/services/chat/capability_guard.rs` | 删除 + 新增 | 删除旧 API（`load_conversation_profile` / `check_capability_with_profile` / `check_capability` + 10 个 `OP_*` 字符串常量 + 5 个旧测试）；新增 5 个 rewind 能力校验测试 |
| `src-tauri/src/commands/conversations.rs` | 修改 | `conversations_fork` 能力校验从 `check_capability(..., OP_FORK_CONVERSATION)` 改为 `resolve_and_check(..., None, Operation::Fork)`；use 增加 `Operation` |
| `src-tauri/src/services/chat_service.rs` | 修改 | `rewind_to_round` 函数上方加一行注释，说明 DB 集成测试待后续建立测试夹具后补充 |
| `src-tauri/src/services/chat/mod.rs` | 修改 | 模块注释移除旧 API 引用，更新使用示例为新 API |
| `.trae/specs/capability-matrix-completion/checklist.md` | 修改 | `src/types.ts` 引用修正为 `src/lib/backend/types.ts` |

### 新增测试函数（capability_guard::tests）

1. `test_rewind_capability_single_stateless_allow` — 断言 `SingleStateless` 的 `rewind==Allow`，`check_capability_mode` 放行
2. `test_rewind_capability_single_mem0_snapshot_limited` — 断言 `SingleMem0` 的 `rewind==SnapshotLimited`，`check_capability_mode` 放行（快照校验由命令层处理）
3. `test_rewind_capability_online_guest_blocked` — 断言 3 个 online guest 变体的 `rewind==Block`，`check_capability_mode` 拒绝
4. `test_rewind_capability_online_host_allow` — 断言 `OnlineStatelessHost` / `OnlineLegacyHost` 的 `rewind==Allow`，`check_capability_mode` 放行
5. `test_rewind_capability_online_mem0_host_snapshot_limited` — 断言 `OnlineMem0Host` 的 `rewind==SnapshotLimited`，`check_capability_mode` 放行

## 2. 改动动机

### 问题 1：回溯功能无专用单元测试

checklist 要求"回溯功能单元测试通过（单人模式、房客禁止、streaming 禁止、mem0 快照校验）"。原仓库仅有矩阵层面测试（mode.rs 的 11 个 + capability_guard.rs 的 9 个），缺少针对 rewind 操作的能力校验专项测试。

`rewind_to_round` 函数内部的 streaming 禁止、collecting 状态、快照存在性等校验依赖 DB，项目无内存 SQLite 测试夹具，无法在纯单元测试覆盖。因此本次仅在纯函数层补充 5 个 rewind 能力校验测试，DB 集成测试留待后续测试夹具建立后补充（已在 `chat_service.rs` 注释说明）。

### 问题 2：能力校验双轨

`capability_guard.rs` 同时存在：
- 旧 API：`check_capability(db, conv_id, op_str)` + `check_capability_with_profile(conv_type, mem_mode, op_str)` + `load_conversation_profile(db, conv_id)`（字符串 match 链）
- 新 API：`resolve_and_check(db, conv_id, member_id, op)` + `check_capability_mode(mode, op)`（纯函数查表）

旧 API 仅 `conversations_fork` 一个生产消费者。改造后 fork 走新 API，旧 API 全部删除，能力校验统一为数据驱动查表路径，消除双轨。

### 问题 3：checklist.md 路径错误

checklist 引用 `src/types.ts`，项目实际路径为 `src/lib/backend/types.ts`，已修正。

## 3. 约束合规审计表

| 约束 | 合规 | 说明 |
|------|------|------|
| C1 Frontend Render-Only | √ | 能力校验全部在后端，前端只接收结果渲染 |
| C2 Zero-Fallback Errors | √ | 旧 API 删除后所有能力校验走 `resolve_and_check` → `check_capability_mode`，Block 显式返回 Err；SnapshotLimited 显式返回 Ok 由命令层追加 `check_snapshot_limited`；无静默回退 |
| C3 Responsiveness | √ | `check_capability_mode` 为 O(1) 静态查表，无锁无 DB；`resolve_mode` 仅 1-2 次轻量 SQL 查询 |
| C4 AI UI Isolation | √ | 本次改动不涉及 AI 渲染层 |
| C5 Mobile Frontend Independence | √ | 仅改动 `src-tauri/` 和 `src/lib/backend/types.ts` 路径引用，未触碰 `src-mobile/` |
| C6 Project Cache Location | √ | 本次改动不涉及缓存写入 |
| C7 PC/Android Coverage | √ | 后端共享，PC 与移动端通过同一 Tauri command 调用；本次改动为后端纯函数测试与 API 收敛，双端均受益；移动端待验收项：移动端前端如需调用 rewind，使用相同 `rewind_to_round` 命令 |

### conversations_fork 改造前后对比

改造前（旧 API，字符串常量 + profile match）：
```rust
capability_guard::check_capability(
    &state.db,
    conversation_id,
    capability_guard::OP_FORK_CONVERSATION,
)
.await?;
```

改造后（新 API，枚举 + 矩阵查表）：
```rust
capability_guard::resolve_and_check(&state.db, conversation_id, None, Operation::Fork).await?;
```

行为等价性：fork 不需要 member_id 区分；single 3 变体中 `SingleStateless` / `SingleLegacy` 的 fork=Allow 放行，`SingleMem0` 的 fork=SnapshotLimited 在 `check_capability_mode` 中放行（与新 API 一致，SnapshotLimited 由命令层追加 `check_snapshot_limited`，但 fork 命令目前未追加快照校验，行为与旧 API 一致——旧 API 对 single/mem0 的 fork 也是放行）；online 6 变体的 fork=Block，与新 API 一致。

注：旧 API 对 single/mem0 的 fork 是"向后兼容放行"（Ok），新 API 对 single/mem0 的 fork 是 `SnapshotLimited`（在 `check_capability_mode` 中也是 Ok）。两者对外行为一致（都返回 Ok），语义更精确（新 API 显式标注为快照受限）。

## 5. 已知限制或后续待办
