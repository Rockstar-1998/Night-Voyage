# 多人房主操作同步前端事件

## 1. 改动摘要

### 涉及文件

| 文件 | 改动类型 | 说明 |
|------|----------|------|
| `src/lib/backend/types.ts` | 新增类型 | 新增 5 个 Room 事件接口：`RoomMessageEditedEvent` / `RoomMessageDeletedEvent` / `RoomRewoundToRoundEvent` / `RoomContextWindowChangedEvent` / `RoomGuestCharacterUpdatedEvent`；`ConversationMember` 接口新增可选字段 `guestCharacterJson?: string`（与后端 `conversation_members.guest_character_json` 列对齐，前端用于缓存房客人设卡） |
| `src/lib/backend/rooms.ts` | 新增函数 | 新增 5 个 `listenRoom*` 监听函数（`listenRoomMessageEdited` / `listenRoomMessageDeleted` / `listenRoomRewoundToRound` / `listenRoomContextWindowChanged` / `listenRoomGuestCharacterUpdated`）+ 1 个 `roomUpdateGuestCharacter` 调用函数；遵循已有 `listen<T>('event', handler)` + `console.debug` 风格 |
| `src/App.tsx` | 修改 | import 新增 5 个监听函数 + `roomUpdateGuestCharacter` + 5 个事件类型；`onMount` 注册 5 个新监听器并加入 `onCleanup`；`handleSwitchPlayerCharacter` 新增房客模式分流（房客调用 `roomUpdateGuestCharacter`，房主/单人走原 `conversationMembersUpdate` 路径） |

### 核心改动点

- **types.ts 新增事件接口**：
  - `RoomMessageEditedEvent`：`{ conversationId, messageId, content }`
  - `RoomMessageDeletedEvent`：`{ conversationId, messageId, roundDeleted }`
  - `RoomRewoundToRoundEvent`：`{ conversationId, targetRoundId }`
  - `RoomContextWindowChangedEvent`：`{ conversationId, contextWindowSize }`
  - `RoomGuestCharacterUpdatedEvent`：`{ conversationId, memberId, character: GuestCharacterCardPayload }`（复用已有 `GuestCharacterCardPayload` 类型，避免重复定义结构）
- **rooms.ts 监听函数**：5 个 `listenRoom*` 函数均使用 `listen<T>` 直接订阅 Tauri 事件，附 `console.debug` 日志，与 `listenRoomContextSnapshot` / `listenRoomSchemaToggle` 等已有函数一致；`roomUpdateGuestCharacter` 使用 `invokeCommand` + `toInvokeArgs`，参数类型为 `{ conversationId, memberId, character: GuestCharacterCardPayload }`
- **App.tsx 监听器注册**（均校验 `payload.conversationId === selectedConversationId()`）：
  - `listenRoomMessageEdited`：房客模式（`activeRoomClientSession()` 存在）下，按 `messageId` 更新 `content` 并清空 `structuredFields`（触发重新解析），置 `isStreaming=false`
  - `listenRoomMessageDeleted`：房客模式下，`roundDeleted=true` 时按 `roundId` 整轮过滤，否则仅过滤单条 `messageId`
  - `listenRoomRewoundToRound`：房客模式下，过滤掉 `roundId > targetRoundId` 的消息；若 `currentRoundState` 的 roundId 超出 target 则置空
  - `listenRoomContextWindowChanged`：房客模式下，更新 `roomClientSession.contextWindowSize`
  - `listenRoomGuestCharacterUpdated`：房主+房客均处理（不检查 `activeRoomClientSession()`），将 `payload.character` 序列化为 JSON 写入对应 member 的 `guestCharacterJson` 字段
- **handleSwitchPlayerCharacter 分流**：
  - 房客模式（`activeRoomClientSession()` 存在）：从 `playerCharacters` 按 id 找到角色卡，构建 `GuestCharacterCardPayload`（`baseSections` 映射 `sectionKey`/`title`/`content`），调用 `roomUpdateGuestCharacter`，不走 `conversationMembersUpdate`
  - 房主/单人模式：走原 `conversationMembersUpdate` + `refreshConversationContext` 路径，保持现状

## 2. 改动动机

多人模式下房主的 5 项操作（编辑消息、删除消息、回溯到某轮、修改上下文窗口、房客更新人设卡）不同步给房客，导致房客看到的会话状态与房主不一致。本次新增 5 个前端事件监听链路，让房客能实时接收房主的操作广播；同时为房客运行期切换人设卡新增 `roomUpdateGuestCharacter` 调用路径（房客不能直接改后端 `conversation_members` 表，必须通过房主转发）。

## 3. 约束合规审计表

| 约束 | 合规 | 说明 |
|------|------|------|
| C1 Frontend Render-Only | √ | 前端仅订阅事件并更新本地渲染状态，不做业务计算；房客人设卡更新通过后端 `room_update_guest_character` 命令转发 |
| C2 Zero-Fallback Errors | √ | 监听器对 `conversationId` 不匹配的事件直接 return（不处理非当前会话的事件，非吞错）；角色卡未找到时 `throw Error` 显式报错；不假装成功 |
| C3 Responsiveness | √ | 事件处理为同步轻量操作（filter/map/setStore），无阻塞；`roomUpdateGuestCharacter` 为异步 IPC 调用 |
| C4 AI UI Isolation | √ | 不涉及 AI 动态 UI 层 |
| C5 Mobile Frontend Independence | √ | 仅改 `src/`，未触碰 `src-mobile/`；移动端覆盖由后续对应任务处理 |
| C6 Project Cache Location | √ | 不涉及缓存写入 |
| C7 PC/Android Coverage | √ | 本任务为 PC 前端部分，移动端前端（`src-mobile/`）需后续对应任务接入相同事件监听；后端事件广播两端共用 |

### 验收方式

1. **类型检查**：tsc --noEmit 无新增错误（首次运行发现 1 个新增 `GuestCharacterCardPayload` 未使用错误，已移除该 import 后复测通过）
2. **事件接口**：5 个新接口字段与任务定义一致，`RoomGuestCharacterUpdatedEvent.character` 复用 `GuestCharacterCardPayload`
3. **监听函数**：5 个 `listenRoom*` 函数风格与已有 `listenRoomContextSnapshot` 一致
4. **监听器注册**：5 个监听器均在 `onMount` 注册、`onCleanup` 清理；`conversationId` 校验前置
5. **房客人设卡分流**：`handleSwitchPlayerCharacter` 房客模式走 `roomUpdateGuestCharacter`，房主/单人走原路径

### 预期效果

- 房主编辑消息 → 房客收到 `room:message_edited`，本地消息 `content` 更新并重新解析
- 房主删除消息 → 房客收到 `room:message_deleted`，按 `roundDeleted` 整轮或单条过滤
- 房主回溯 → 房客收到 `room:rewound_to_round`，过滤掉 targetRoundId 之后的消息
- 房主改上下文窗口 → 房客收到 `room:context_window_changed`，更新 `roomClientSession.contextWindowSize`
- 房客切换人设卡 → 调用 `roomUpdateGuestCharacter`，房主收到 `room:guest_character_updated` 更新 member 的 `guestCharacterJson`
- 房主/单人模式切换人设卡 → 走原 `conversationMembersUpdate` 路径，行为不变

## 5. 已知限制或后续待办

1. **移动端未覆盖**：本任务仅改 PC 前端（`src/`），移动端前端（`src-mobile/`）需后续任务接入相同的 5 个事件监听和 `roomUpdateGuestCharacter` 调用，以满足 C7 双端覆盖。
2. **`guestCharacterJson` 仅前端缓存**：后端 `ConversationMember` 结构体未序列化 `guest_character_json` 字段，因此 `refreshConversationContext` 拉取的 member 列表不包含该字段。当前实现下，房主刷新会话上下文后会丢失房客人设卡缓存（需等待下一次 `room:guest_character_updated` 事件重新填充）。若需持久化展示，后续应在后端 `ConversationMember` 结构体补充该字段序列化。
3. **`RoomGuestCharacterUpdatedEvent` 无 `activeRoomClientSession()` 门控**：房主模式下 `activeRoomClientSession()` 为 null，但房主仍需处理该事件（接收房客的人设卡更新），因此该监听器未做房客模式校验，仅校验 `conversationId`。
4. **`structuredFields` 清空策略**：`listenRoomMessageEdited` 收到编辑事件后清空 `structuredFields`（设为 `undefined`），让 `MessageFormatRenderer` 基于新 `content` 重新解析。若编辑后的内容本身是结构化输出，需依赖渲染层的 content 解析能力。
