## 2. 改动动机

### 2.1 架构方向变更：trait 对象 → const 数据驱动能力矩阵

**问题**：`capability-unit-refactor` POC 建立的 trait-based pipeline 框架违反 Rust 官方"组合而非继承"编程思想：
- `ChatPipeline` trait + `Box<dyn ChatPipeline>` 是继承式设计（默认实现 + 覆写）
- vtable 开销
- 能力校验散落在各 pipeline 实现中，难以一览全貌

**解决**：改为 const 数据驱动组合式设计：
- 能力矩阵为 `const MODE_CAPABILITIES: [ModeCapabilities; 9]` 编译期常量
- 能力校验为纯函数查表 `MODE_CAPABILITIES[mode as usize].get(op)`
- 执行层共享 `ChatService`，无模式专属 pipeline
- 9 种模式 × 7 操作矩阵一目了然，无 match 链

### 2.2 能力矩阵完整化

**问题**：POC 仅收紧 single/stateless 与 single/legacy，其余 7 种模式能力矩阵未落地。

**解决**：按 `能力与模式一览表.md` 定义全部 9 种模式的 const 能力集，含 online host/guest 区分（通过 `member_id` 查询 `conversation_members.member_role`）。

### 2.3 回溯功能（新增）

**问题**：矩阵中「回溯到某轮对话」是尚未实现的新功能。

**解决**：实现 `rewind_to_round` 命令，逻辑为"丢弃目标轮次之后的所有消息，回到用户指令的轮次中"：
1. 校验目标轮次存在、非 collecting、无活跃 streaming
2. 删除 round_index > target 的所有轮次及其消息
3. 删除目标轮次 assistant 消息（保留 user 消息）
4. 重置目标轮次为 collecting 状态
5. mem0 模式额外校验快照存在（SnapshotLimited）

## 5. 已知限制或后续待办

### 5.1 已知限制

1. **mem0 模式回溯未做文件级 DB 回滚**：用 SQL 删除 + SnapshotLimited 校验作为安全机制。vector DB 可能与 SQL 数据不一致，但快照窗口限制可接受（用户仅能在快照存在的轮次内回溯）。决策见 `tasks.md` Task 6。

2. **回溯 DB 集成测试缺失**：`rewind_to_round` 的 streaming 禁止校验、collecting 状态校验、`check_snapshot_limited` 的快照存在/不存在分支、`delete_rounds_after` / `reset_to_collecting` 的 SQL 逻辑均依赖 DB，项目无内存 SQLite 测试夹具，本次未覆盖。已在 `chat_service.rs:936` 加普通注释说明（无 TODO/FIXME 标记）。

3. **online 房客不自动刷新回溯**：后端回溯命令不内嵌广播（现有 `room_broadcast_round_state` 是前端驱动广播模式），房客无法实时感知 host 回溯操作。房客依赖现有轮询/事件刷新机制自然同步。决策见 `tasks.md` SubTask 5.7 和 SubTask 9.5。

4. **错误提示用 `window.alert`**：与项目现有 `handleForkMessage`/`handleDeleteMessage` 等保持一致，项目无 toast 系统。如需更优雅的提示，需另立任务统一改造。

5. **前端无测试框架**：`package.json` 仅含 vite/typescript/solidjs/tailwindcss，无 vitest/jest。`selectProfile` 的逻辑等价性由后端 `mode.rs` 的 11 个矩阵测试间接保证。

6. **既有 tsc 错误未修复**：基线 15 个错误（App.tsx 5 + CharacterSidebar 7 + SchemaConfigPanel 2 + WorkspaceTransitionStage 1）与本任务无关，未在本次修复。
