## 1. 背景与核心目标

Night Voyage 是一个基于 `Tauri 2.0 + Rust` 核心与 `SolidJS` 双端宿主的跑团（TRPG）与角色扮演应用。在经历了单轮经典对话、蓝图 DAG 条件分流编译、以及 MEM0 动态记忆托管之后，系统正式迈向 **Agent 智能体化编排**。

传统跑团大模型应用存在三大核心顽疾：
1. **全知污染**：大模型直接读取全量世界书与剧情大纲，导致小商贩、巡逻卫兵等 NPC 拥有“上帝全知视角”，产生出戏和严重幻觉；
2. **一次性生成粗糙与自抄袭**：长篇跑团叙事中，模型一次性吐出正文易发生设定漂移、情绪生硬；多轮续写或审阅时，小模型频繁复读上一段开头的文字（自抄袭）；
3. **随口判定与数值失真**：模型随口胡诌骰子点数和战斗胜负，缺乏确定性规则；
4. **超高频调用下的账单风控**：多 Agent 协作和向量记忆召回必然导致 Token 消耗成倍激增，对于商业计费 API 必须实施最严肃的风险提示。

本方案系统性吸收 **TauriTavern 的架构严密性（Rust 调度、Subagent 契约、沙盒快照）** 与 **aisandboxgame 的沙盒跑团精髓（阶段裁剪、确定性 D20、Layer 1 涂黑）**，打造高可用、永不假死的跑团 Agent 体系。

### 2.1 坚决捍卫 C1/C6 约束：Rust 核心调度器与沙盒工作区

#### (1) C1 约束（Frontend Render-Only）
- **所有 Agent 调度逻辑、子代理派发、状态机推进全部封装于 Rust 后端**（`src-tauri/src/services/`）。
- 前端（`src/` 与 `src-mobile/`）仅作为无状态的纯渲染宿主，通过 Tauri Event 接收调度进度事件（如 `agent:delegating`、`agent:critic_feedback`、`dice:rolled`），通过 UI 组件流式绘制，严禁在前端编写任何多代理决策逻辑。

#### (2) C6 约束下的沙盒工作区文件隔离（Workspace Sandbox）
为保障长篇小说生成、多轮剧本打磨的回滚、审计与复现，系统在 Rust 端建立物理沙盒工作区：
*   **物理存储路径（严格执行 C6 约束）**：
    绝对禁止写入 `C:\Users\...` 系统盘。沙盒统一建立在统一运行时缓存根目录下：
    `D:\software_cache\night_voyage\sandbox\<conversation_id>\`
*   **三级目录隔离规范**：
    *   `plan/`：存放导演大纲、意图解析草案、检定任务规格单（`task_spec.json`）；
    *   `scratch/`：存放草稿写手的初稿、中间思考过程、Critic 的批注日志（`critique_v1.json`）；
    *   `output/`：存放最终经过润色、校验合格的定稿正文快照（`chapter_final.md`）。
*   **版本演进与 Checkpoint 回滚**：
    每次会话推进在沙盒中以时间戳和轮次索引记录原子版本（`v1`, `v2`, `v3`）。当玩家在 UI 点击“回滚”或“重试本轮”时，Rust 调度器直接以沙盒快照进行还原，确保每次生成与重试皆有据可查。

### 2.2 模式一：导演-演员模式（Director-Actor / Return-mode Subagent）

#### (1) 业务痛点与心智隔离
传统跑团最大的代入感破坏是 NPC 拥有“全知视角”。酒馆老板或路过盗贼如果能感知全局主线，对话必然出戏。导演模式通过 **Return-mode Subagent** 实施严格的信息分级与权限隔离。

```
[玩家输入] ──> "我想打听黑石矿山深处的密道在哪"
                     │
                     ▼
┌────────────────────────────────────────────────────────┐
│ 1. 主导演 Agent (Director / DM 主持人)                  │
│  - 拥有全量上下文：完整大纲、世界书、全局 MEM0 剧情事实│
│  - 规则仲裁：判定是否需要检定，发起 D20 骰点工具       │
│  - 阶段裁剪：在 50+ 世界书条目中仅提取【老铁匠的秘密】 │
│  - 编写【导演即时小纸条】 (Director's Note)            │
└──────────────────────────┬─────────────────────────────┘
                           │ 调度调用: agent.delegate(task_spec)
                           ▼
┌────────────────────────────────────────────────────────┐
│ 2. 演员 Subagent (Actor / 老铁匠)                      │
│  - 局部心智视野：仅传入老铁匠角色卡 + 导演小纸条       │
│  - 物理剥夺全局工具与主对话提交权                      │
│  - 以地道口吻演绎，产出台词、动作描写与心理反应        │
└──────────────────────────┬─────────────────────────────┘
                           │ 提交交付: task.return(dialogue_payload)
                           ▼
┌────────────────────────────────────────────────────────┐
│ 3. 主导演汇总统筹并定稿 (Director Finalize)            │
│  - 汇聚老铁匠台词、环境烘托描写、骰点结果与物品变动    │
│  - 统一提交前端渲染并落库                              │
└────────────────────────────────────────────────────────┘
```

#### (2) 交互协议契约
*   **`agent.delegate`（导演派发任务）**：
    ```json
    {
      "subagent_id": "blacksmith_durin",
      "scoped_character_card": { "name": "老铁匠杜林", "personality": "粗暴、多疑、爱钱" },
      "director_notes": "【指令】：你畏惧矿山里的吸血蝙蝠，对玩家的要求充满怀疑；绝不要提密道就在锻炉水槽下。",
      "recent_dialogue_slice": [ "...最近 3 轮台词..." ],
      "required_return_schema": ["dialogue", "action", "inner_thought"]
    }
    ```
*   **`task.return`（演员交付结果）**：
    ```json
    {
      "inner_thought": "矿山深处？这小子是在找死，还是打着什么别的主意？",
      "action": "重重地将火钳砸在铁砧上，火星四溅。",
      "dialogue": "矿山？嘿，听我一句劝，外乡人，有些秘密比铸铁还要烫手，滚回你的马车上去！"
    }
    ```

### 2.3 模式二：剧本模式（Scriptwriter / Handoff 接力流水线）

#### (1) 业务痛点与工作逻辑
长篇跑团故事如果依赖单次 Prompt 生成，经常出现情绪突变、伏笔遗忘、文风漂移。剧本模式通过 **Handoff 接力模式**，在同一个会话生命周期内串行流转，实现专业作家级的多重打磨：

```
[玩家行动推进]
     │
     ▼
┌────────────────────────────────────────────────────────┐
│ 1. Drafter (初稿生成 Agent)                           │
│    快速起笔，铺陈冲突与情境，输出草稿 1.0              │
└──────────────────────────┬─────────────────────────────┘
                           │ handoff(draft_text, metadata)
                           ▼
┌────────────────────────────────────────────────────────┐
│ 2. Critic (审阅批注 Agent)                             │
│    对照角色设定、世界观禁忌、文风节奏进行结构化批注    │
└──────────────────────────┬─────────────────────────────┘
                           │ 是否通过？
                           ├── 是 (Passed) ──────────────────────────┐
                           └── 否 (Feedback 批注修改意见)             │
                                     │                               │
                                     │ handoff(draft + feedback)     │
                                     ▼                               │
┌────────────────────────────────────────────────────────┐           │
│ 3. Refiner (终稿润色 Agent)                            │           │
│    依据批注逐段精修润色，消除硬伤，输出版本 2.0        │           │
└──────────────────────────┬─────────────────────────────┘           │
                           │                                         │
                           └─────────────────────────────────────────┤
                                                                     │
                                                                     ▼
                                                   ┌───────────────────────────────────┐
                                                   │ 4. workspace.commit (沙盒统一提交) │
                                                   │   写入数据库正式消息表并呈递前端  │
                                                   └───────────────────────────────────┘
```

#### (2) 硬性熔断与防护机制（Guardrails C2/C3）
*   **`max_handoff_depth = 2`**：
    严格限制审阅打磨的最大迭代深度为 2 轮。若达到第 2 轮哪怕 Critic 仍有挑剔意见，Refiner 润色后也必须执行 `workspace.commit` 强制交付，严防无限死循环导致 Token 瞬间炸裂与界面假死。

### 2.4 吸收 aisandboxgame 跑团精髓

#### (1) 阶段性 Prompt 裁剪机制（Stage-Specific Prompt Pruning）
*   **现象与根因**：把全量 50+ 世界书条目、全局系统提示词、100 楼聊天历史同时塞给模型时，小模型注意力极度涣散，角色口吻严重同质化。
*   **裁剪规范**：
    *   **角色演义阶段**：仅注入当前出场角色的单张卡片、导演下发的 100 字即时小纸条、以及最近 2~4 轮近景台词切片，剔除宏观历史与未在场角色。上下文体积压缩 80%~90%，角色扮演神韵提升数倍。
    *   **判定结算阶段**：剔除所有环境描写指令，仅灌入中立仲裁规则与数值属性。

#### (2) Layer 1 Redaction（局部涂黑防自抄袭算法）
*   **现象与根因**：在剧本模式多轮修改、正文接力续写时，大语言模型极易逐字抄袭前一段的开头（ABA 抄袭），产生严重的词句复读。
*   **遮盖与还原算法**：
    1.  当历史叙事段落超过 80 字时，将其发送给模型前进行**腹部掏空遮蔽**，仅保留前序 50 字作为语气和情境的承接锚点：
        ```
        "[此段前序叙事已被运行时遮蔽（原文 320 字，玩家已阅读）。末尾承接锚点(40字)：
         '...铁匠冷冷盯着你，粗糙的大手悄悄握紧了身旁的铁锤。']
         请紧承上述锚点自然推进后续剧情，严禁重述、严禁复读上述文字！"
        ```
    2.  模型输出完毕后，Rust 调度器在内存中即时执行 `restore()` 复原完整历史，对外呈现无缝衔接的完整长篇叙事。

#### (3) 确定性 D20 骰点检定（Deterministic Dice Mechanics）
*   **拒绝伪跑团**：坚决摒弃让模型在叙事中“随口编造点数并宣布胜负”的不可信做法。
*   **计算闭环**：
    1.  Agent 识别到对抗或检定需求，发起 `tool_call: dice_roll({ formula: "1d20+3", skill: "交涉", dc: 14 })`；
    2.  Rust 后端调用 CSPRNG 真随机数发生器掷出骰子，按规则硬编码计算：
        $$\text{Total} = \text{Roll}(1 \dots 20) + \text{Modifier}$$
        $$\text{Result} = \text{Total} \ge \text{DC} ? \text{Success} : \text{Failure}$$
    3.  Rust 通过 Tauri Event 向前端广播，在聊天列表或悬浮层渲染动效 **D20 检定徽章卡片**；
    4.  检定结果回填给后序叙事 Agent 作为既定事实进行文学描写。

### 2.5 复合大剧场模式（Director + Scriptwriter 复合装配）

系统支持将导演模式与剧本模式串联激活：
1.  **导演统筹**：主导演 Agent 仲裁局势、触发 D20 骰点、执行世界书裁剪，向选定 NPC 下发小纸条（`agent.delegate`）；
2.  **写手初稿**：演员 NPC 结合小纸条产出台词与场景初稿（Drafter）；
3.  **监制审阅与润色**：Critic 审核人设一致性并批注，Refiner 润色后统一提交 `workspace.commit`。

## 3. 高消耗 Token 激增红字强警示（强制风控）

### 3.1 触发机制
在单次对话推进中，系统实时监控以下 **3 项高消耗能力** 的启用情况：
1.  **纯导演模式**（单轮对话至少触发 2 次不同角色的 LLM 调用：导演 + 演员）；
2.  **纯剧本模式**（单轮对话至少触发 2~3 次 LLM 调用：初稿 + 审阅 + 润色）；
3.  **MEM0 长期记忆模式**（单轮对话触发 3 路语义检索 + 后台异步事实反思提取）。

**判定规则**：
$$\text{HighCostCount} = (\text{DirectorActive} ? 1 : 0) + (\text{ScriptwriterActive} ? 1 : 0) + (\text{Mem0Active} ? 1 : 0)$$

当 $\text{HighCostCount} \ge 2$ 时，系统**强制触发醒目红色高风险警示**。

### 3.2 规范文案与视觉呈现规范
*   **强制文案（一字不差）**：
    > ⚠️ **这会导致消耗的TOKEN激增，尤其是对于按次计费的API来说，而这仅仅只是为了一次回答，请仔细斟酌这是否值得！**
*   **前端呈现规范**：
    *   **色彩体系**：高对比度警示红（`text-rose-500 dark:text-rose-400`，辅以 `bg-rose-500/10 border border-rose-500/30` 边框）；
    *   **微交互动效**：进入视图时使用 Motion One 执行平滑淡入 + 柔和呼吸脉冲动效，不可阻塞主线程；
    *   **展示点位**：
        1.  **新建会话窗口**（PC 端 `NewChatModal.tsx` / 移动端 `MobileNewChatModal.tsx`）；
        2.  **会话属性抽屉**（PC 端 `RightDrawer.tsx` / 移动端模式切换面板）；
        3.  **输入框上方提示条**：处于高危组合时常驻提示。

## 5. 项目硬性约束合规审计（Guardrails C1–C7）

| 约束 | 合规方案 | 说明 |
| :--- | :---: | :--- |
| **C1 Frontend Render-Only** | √ | 导演裁决、演员派发、草稿循环、D20 算术与沙盒管理全在 Rust 后端，前端纯渲染 |
| **C2 Zero-Fallback Errors** | √ | 任何子代理超时、检定失败或沙盒读写异常显式上抛报错，严禁静默伪成功 |
| **C3 Responsiveness** | √ | 所有多代理调度基于 Tokio 异步通道，分段流式输出，UI 线程 0 假死 |
| **C4 AI UI Isolation** | √ | 交互式浮窗与沙盒 UI 严格限制在 `iframe` (sandbox 隔离) 中渲染，禁止样式污染 |
| **C5 Mobile Independence** | √ | PC 端 (`src/`) 与移动端 (`src-mobile/`) 各自独立实现模式切换与红字警示，零 UI 耦合 |
| **C6 Project Cache Location** | √ | 沙盒工作区文件严格落在 `D:\software_cache\night_voyage\`，严禁写入 C 盘 |
| **C7 PC/Android Dual Coverage**| √ | 后端统一暴露 Tauri Command / Event 接口，双端同步适配桌面大屏与触控体验 |
