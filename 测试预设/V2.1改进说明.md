# V2.0 → V2.1 改进说明

- 日期：2026-08-31
- 产出：`Night Voyage 全能进阶核心预设 V2.1.nvpreset.json`（57 节点 / 81 边，结构校验通过）
- 依据：对 `src-tauri/src/services/blueprint_executor.rs`、`prompt_compiler.rs`、`provider_adapter.rs` 及前端 `messageFormatter.ts`、`MessageFormatRenderer.tsx` 的执行器语义查证。

## 一、执行器语义查证结论（改动依据）

1. **提示词最终按节点 priority 降序拼装**；连线（DFS 可达性）只决定节点是否激活。同 priority 保持遍历相对序。
2. **group_gate 空选合法直通**到汇合节点，链路不会断。
3. **带 Schema 字段的蓝图在编译期强制切 structured_json**，顶层 responseMode 是摆设（V2 顶层写的 pseudo_xml 实际从未生效）。
4. **叙事正文字段按字段名精确匹配**：基线只认 `thinking`/`text` 两个名字；前端聊天气泡正文只认 `display.body=true` 的 string 字段。
5. **前端结构化渲染只支持**：string、扁平 object（值全为 string）、纯 string 数组（渲染为可点击选项按钮）。对象数组会被静默丢弃。
6. **采样参数优先级**：蓝图节点 > provider override > 预设顶层，逐字段 Some 才覆盖。
7. **schema_field 不输出提示词文本**；`order` 决定 schema 属性排序；模块未选中时其字段不进 schema（无残留）。
8. **context_included**：控制上一轮该字段值是否注入下轮上下文；map 缺失键默认 true，必须显式 false 才能屏蔽。

## 二、修复的 V2 现存 Bug

| # | 问题 | 修复 |
|---|------|------|

| 3 | `n_rules`（终极执行守则）无任何入边，从 start 的 DFS 不可达 → 守则是死文本 | 接入链尾：bdry 三支路 → rules → thinking |

## 三、六阶段管线重排（priority 即提示词顺序）

```
阶段一 角色与世界   core(100) → multi(95)
阶段二 思维链头     cot_framework(92) 三步推演【新增】
阶段三 思维链可选   driver(88) → res(85) → proxy(82,转述语义补强) → anti_spoil(81)
                    → status_read(80) → todo_read(80)【新增·读半】
阶段四 思维链尾     空槽位（预留"输出前自检"模块位，默认不放）

                    → word(68, 含新增 unlimited 自判档位) → bdry(65)

                    → rules(10 收口) → thinking(-2) → text(-1) → params → end
```

代理门四档即转述控制（沿用现有，不新增转述门），内容补强：全禁言=落点直续不重述；可代行动=引号原话原样保留+括号元指令隐式融入；扩写推演=指令/OOC 不得扩写成玩家对白；全代言=重大决定须有已表达意图为依据。

## 五、Schema 变更

| 字段 | V2 | V2.1 | 原因 |
|------|----|----|------|
| thinking | order 0, context_included true | order -2, context_included **false** | 对齐基线约定；阻断思维链回灌 |
| 正文 | field_name「正文」, display 缺 body | field_name `text`, order -1, body=true | 消灭基线双叙事；前端按 body 渲染气泡正文 |
| status_bar | object {mood, health} | object **map**：additionalProperties string，键=角色名，值=「情绪…｜体力…｜理智…」 | 按角色一条（用户决策 A）；对象数组前端会静默丢弃，map 形式渲染为键值面板 |
| options | object 空 properties（坏的） | array of string | 前端渲染为可点击选项按钮 |
| todo_list | array of string（不变） | 同左，描述补"已完成不再输出、每条具体可执行" | 注意：前端把字符串数组渲染为按钮列表，TODO 会显示成可点击条目，暂可接受 |

## 六、验收方式

1. 在蓝图编辑器导入 V2.1，确认无红线（mode_switch 三端口已连、各 gate 选项端口齐全）。
2. 发起对话，检查输出：thinking 字段应出现三步推演结构；`text` 字段为正文且直接渲染在聊天气泡（不再是「正文」标签块）；status_bar 显示为按角色名的键值面板；options 显示为可点击按钮。
3. 对照提示词预览（如有）确认顺序：核心引擎 → 多人 → 三步推演 → 驱动/阻力/代理 → 状态/TODO 读取 → 视角 → 文风 → 镜头三拍 → 字数 → 边界 → 平行/回写/选项规则 → 终极守则。
4. 多玩家联机房间验证逐玩家拆解与逐人起点镜头。
5. 连续 5 轮观察：状态栏不跳变、TODO 逐轮推进、无重复正文。

## 七、已知限制与后续

1. **思维链预算**：thinking 走 schema 字段（非原生思维链），与正文共享 16384 max_tokens；多角色+长篇档若截断，优先上调 max_tokens 或降低字数档位。原生思维链通路（anthropic thinking_enabled）未启用，保持 null。
2. **思维链尾自检模块**：槽位已留（阶段四），需要时加一个 priority≈30 的"输出前自检" prompt 节点挂入链尾即可。
3. **杀八股模块**：未加入（五预设分析中的头号共性）。建议后续做成 group_gate 或直接并入文风门选项。
4. **防雷同**：由 frequency_penalty 0.15 承担，实测不够再调 0.3–0.5。
5. **NSFW 细化**：边界门现有三档保持，深入规则延后（用户决策）。
6. status_bar 的 map 值是单字符串，若将来前端支持对象数组，可升级为结构化字段。
